<objective>
Enforce the IAMF v1.1.0 temporal rules on Parameter Block duration, parameter coverage and trim
placement in the high-level encoder. Research 260913-n56 names these rules P1-P5, T3 and T4.

Research ran every probe against the pinned `iamf-tools:v2.1.0` `decoder_main` and found three gaps:
- `EncoderBuilder` and `EncodingWriter` accept Parameter Blocks whose duration does not match the frame.
- They accept parameter substreams with gaps or late starts.
- They accept start and end trims placed mid-stream.

`decoder_main` rejects the first two only from the second temporal unit on, and it cannot see trim
placement at all. The crate must therefore enforce these rules itself.

Locked decisions from the orchestrator:
- D-LOCKED A1 (tie-break): the builder requires `parameter_rate == output sample rate`, and block
  duration must equal `num_samples_per_frame`. The spec permits scaled rates (index.bs:863-865, :1916),
  but pinned `decoder_main` rejects them. Record that disagreement in a `// ref:` comment and in the
  deferred-items file.
- D-LOCKED rule set: P1 and P2 go in `build()`. P3 and P5 go in the preflight. P4, T3 and T4 are
  `EncodingWriter` state that updates only after a successful push. All new kinds are payload-free.
- D-LOCKED boundary: the low-level writers, golden fixtures and DIFF-LEDGER.md do not change.
- D-LOCKED test repair: `tests/encoder_streaming.rs` `mode_1_submitted_blocks_require_non_empty_positive_exact_tiling`
  changes from duration 10 to duration 128.
- D-LOCKED deferrals: Opus `pre_skip` vs start trim, `validate()` findings, uncoupled stereo, and
  scaled `parameter_rate` are written to deferred-items. None of them is implemented.

Discretion choice: six distinct kinds, keeping P5 separate from P4. Each maps to a separate iamf-tools
diagnostic, so a caller can tell a duplicate from a coverage gap.

Purpose: API-07 promises that each temporal submission validates "rate, duration and exact tiling".
API-06 promises "trim agreement and temporal-unit alignment". This plan makes both true, so the Core
Value is not at risk from multi-unit exports that the reference rejects.

Output: 6 error kinds, 2 build checks, 5 preflight checks with committed state, about 12 new tests,
1 repaired test, and a deferred-items file.
</objective>
