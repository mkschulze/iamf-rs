Five of the thirteen corrections land here, and one of them reorders the plan's own tasks.

- **Correction 12 — assumption A1 is a gating task.** Research's highest-risk `[ASSUMED]` claim is
  that the 24-bit float→int conversion in the reference's plane-to-stride output is exact. The 16-bit
  round trip was proven by execution (0 differing samples of 16000); **24-bit was not tested**. D-18
  chose 24-bit big-endian specifically to cover DESC-03's endianness sense, so if the conversion is
  inexact the answer is a `CONFORMANCE-GATE.md` entry, **not** a silent downgrade to 16-bit that
  abandons the coverage 24-bit was chosen for. Task 1 tests it first, before the fixture is frozen.
- **Correction 2 — `libiamf` applies a −1 dBTP peak limiter unconditionally.** It is created in the
  decoder-open call with a 1 ms attack, a 200 ms release and 240 samples of look-ahead. Below
  threshold the gain is exactly 1.0 and the path is bit-exact; above −1 dBFS it engages for up to
  201 ms and the sample-identity assertion fails with a diffuse, amplitude-only, channel-uniform
  error that reads like a rounding or endianness bug in our code. The linear threshold is
  approximately 0.8913. **The fixture's per-channel index pattern must peak at or below −6 dBFS**, and
  the harness must pass `-disable_limiter` as well. Both, and the harness must document why —
  otherwise a later maintainer raises the amplitude "to make the signal more distinguishable" and
  reintroduces the failure.
- **Correction 9 — the 5.1 fixture needs TWO layouts.** Sound System B (0+5+0) is the comparison
  target; Sound System A (0+2+0) is mandatory because `iamf-tools` hard-checks "every sub-mix must
  have a stereo layout" on write. Two layouts means two `Loudness` blocks, both with caller-supplied
  numbers. Easy to miss because `test_000003` is stereo, so its single mandatory layout doubles as
  its target.
- **Correction 8 — there is no probe binary.** CONF-06 goes through `decoder_main`'s parse path;
  plan 01-02 recorded the observable that signals a parse failure, and this plan asserts on that
  observable rather than on the exit code.
- **Correction 11 — D-19's "the decoder's output IS our input" holds by construction.** The 5.1 →
  Sound System B render matrix is the 6×6 identity and the output order is `L, R, C, LFE, Ls, Rs`.
  So the fixture is authored in that order and the comparison is direct sample-for-sample equality
  with nothing to tune.

Also resolved here: research **open question 3** — whether `assert_conformant` runs `iamfdec` once or
twice. It runs **twice**: `-disable_limiter` for the sample-identity assertion, and the default
(limiter on) for a second, weaker assertion that the decode succeeds and the sample count matches.
That way a future limiter-engaging fixture fails loudly instead of being masked by the flag.

Build the fixture, the dumper and the golden layer.

**`tests/fixture.rs` — the D-18 configuration**, expressed as one function returning
`(DescriptorSet, Vec<i32>)` so `assert_conformant` and the golden test drive the identical input.
Every one of D-18's four properties gets a comment saying which failure it detects, because each
exists to catch a specific bug and a later maintainer will otherwise "simplify" one away:
- **Two Codec Configs, one Audio Element** — because a two-element fixture makes the decoded PCM a
  mix, and predicting a mix requires rendering, which is out of scope.
- **5.1, not stereo** — because the phase's highest silent-failure risk is BCG packing order, and
  stereo cannot detect it: one coupled pair, zero mono channels, nothing observable. 5.1 gives two
  coupled pairs and two monos.
- **24-bit big-endian** (subject to Task 1's recorded result) — because `sample_format_flags == 0`
  means big-endian, the opposite of a WAV-shaped assumption, and a 3-byte big-endian sample is where
  that gets written wrong. 16-bit hides half the mistake.
- **Non-multiple length** — because it forces `trim_at_end > 0`, and with `trim_at_start = 0` the two
  values differ, which is the only way a swapped write order is detectable.
Add a fifth comment for the property research added: **peak at or below −6 dBFS**, because
`libiamf`'s −1 dBTP limiter is created unconditionally and engages for up to 201 ms above threshold,
producing an amplitude-only, channel-uniform diff that reads like a rounding bug in our code. Say
plainly that raising the amplitude "to make the signal more distinguishable" reintroduces it.

Consult `CONFORMANCE-GATE.md` for plan 01-02's recorded answer on the unreferenced Codec Config. If
`encoder_main` accepted it, keep the two-config design with the element referencing the first. If it
refused, adopt whichever fallback 01-02 recorded and carry its caveat into `DIFF-LEDGER.md` — the
arbitrary-OBU hook forces the injected OBU after all normal ones, so ordering becomes positional and
DESC-08's ascending-id property is no longer what is being observed.

**D-19's diagnostic, not a knob.** Write the input PCM in the decoder's documented output order —
`L, R, C, LFE, Ls, Rs` for Sound System B — cited in the harness with both sources. On a mismatch,
run a diagnostic that tests whether *some* permutation of the decoded channels would have matched,
and report `channels scrambled: chN and chM` naming the swap. Report it; never apply it. A permutation
constant is a knob, and the cheapest-looking fix for a failing comparison is to turn the knob until it
goes green, which absorbs a real BCG packing bug into the harness and ships it. No knob, no knob to
turn.

**`src/dump.rs` — the annotated structural dumper (D-20).** `pub fn dump_annotated(bytes: &[u8]) ->
Result<String>` walks the OBUs with `find_obu_boundaries`, parses each, and emits one line per field:
absolute offset, field name, decoded value, raw hex. Output format is Claude's discretion; make it
deterministic, stable under re-run, and diff-friendly — fixed-width offset column, one field per
line, no timestamps and no absolute paths. It doubles as the debugging tool for the diff-ledger work
in Task 3, so a wrong byte should be locatable from the dump alone. Put D-20's caveat in the module
doc in the imperative: **the dump is self-consistent with the writer, so it aids review, never
correctness.** The same caveat applies to the golden hash — a golden this crate generated is change
detection, not conformance evidence.

**`tests/fixtures/golden/` — the three committed artifacts (D-20, GUARD-09).** Commit the `.iamf`
fixture, a file holding its SHA-256, and the annotated dump. The dump is what makes an output change
a reviewable PR diff, which is GUARD-09's entire stated rationale and which neither a bare hash (a
one-line diff that explains nothing) nor a bare binary blob delivers. Compute the hash with the
platform tool in CI or a dev-dependency; **do not add a hashing crate to the shipping graph** and do
not hand-roll SHA-256 — it is a change-detection digest, not a security boundary.

**`tests/golden.rs` — GUARD-09 and GUARD-10.** Regenerate the fixture, hash it, and compare against
the committed hash; on mismatch print the first differing offset and a window of the annotated dump
around it, so the failure is actionable. Add the same-process double-encode test: build the fixture
twice in one process and assert byte-identity — the only cheap check that catches per-process hash
seeding, which is precisely why `HashMap` is banned crate-wide. Both tests are offline and require no
reference binary, so they run on all four targets in the PR gate (CONF-10).

Wire the golden test into `.github/workflows/ci.yml` on all four matrix entries. The matrix from plan
01-01 now has the golden it was built to compare.
